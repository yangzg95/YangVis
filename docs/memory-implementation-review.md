# 长期记忆与会话摘要实现复盘

从一个「固定 6 轮窗口、窗口外历史直接消失」的对话系统，到具备滚动摘要与跨会话长期记忆。本文记录实现方案、复用的既有惯例，以及过程中规避掉的 17 个坑。

## 方案一句话

**两张表 + 两处注入 + 一个后台任务** —— `chat_summary` 存窗口外历史的滚动摘要，`user_memory` 存跨会话的用户事实；回答时拼进 system prompt；每轮回答落库后由 `after_answer_task` 在请求外重算摘要、提取记忆。

## 数据流

```
用户消息 → ReAct 回答 → assistant 消息落库
        ↓
fire_and_forget(after_answer_task)   ← 请求外执行，自开 session
        ↓
  ┌─────────────────────────┬──────────────────────────┐
  │ 摘要全量重算              │ 记忆提取（JSON 增删改）      │
  │ → chat_summary          │ → user_memory            │
  └─────────────────────────┴──────────────────────────┘
        ↓
下一轮 stream_answer：人设 → 记忆 → 摘要 → 引用规则 → 运维规则
```

智能体侧只加一个 `use_memory` 开关，与 `use_knowledge` / `use_ops` 完全同构。

## 实现方式：不引入新范式，全部沿用代码库既有惯例

| 既有惯例 | 本次应用 |
| --- | --- |
| 记忆即表，`owner_id` 作用域 | 两张新表全走 `_scope()`，越权访问 404 不 403 |
| 能力即开关，规则后缀统一追加 | `use_memory` 字段 + `MEMORY_RULES`（同 `_CITATION_RULES` 模式） |
| 硬约束留在 prompt 末尾 | 注入顺序：人设 → 记忆 → 摘要 → 引用规则 → 运维规则 |
| 后台任务自己开 session | `after_answer_task` 复刻 `index_document_task` 形态 |
| 字符数预算，不用 tokenizer | 摘要输入 `12000`、正文 `1500`、提取单条 `2000`、注入 `30` 条 |
| 启动时幂等迁移 | `migrate_schema()` 补列，`create_all` 建新表，seed 刷开关不动 `enabled` |
| 一次性长输出用非流式 + 长超时 | `_ask_text` 参照 resume 的 `_ask`，`120s` |

## 规避掉的坑

### 正确性（5）

1. **增量摘要的 checkpoint 脏数据。** 存「摘要到第几条」的话，用户手动改历史后摘要永久过期，worker 切换也丢状态。**→ 全量重算、无 checkpoint**，幂等自愈；只有历史超过 `12000` 字符才退化为「旧摘要 + 尾部」合并。
2. **SSE 流挂不了 BackgroundTasks。** FastAPI 的后台任务在流式响应里语义别扭，请求级 session 也早关了。**→ `fire_and_forget` 挂在 `stream_answer` 内部**，三个调用入口（提问 / 重试 / 确认续答）自动全覆盖，任务自开 session。
3. **`asyncio.create_task` 被 GC 回收。** 事件循环只弱引用任务，没跑完就可能被回收。**→ 模块级强引用集合** + done 回调回收。
4. **chat ↔ memory 循环导入。** chat 模块级依赖 MemoryService，memory 的后台任务又需要 ChatService。**→ 任务体内延迟导入**（代码库已有同款先例）。
5. **同批 operations 重复 add**（冒烟实测抓到的真 bug）。去重只查了提取前的快照，本批新增不在里面。**→ 规范化内容集合**，已有记忆与本批新增一起查重。

### 上下文质量（6）

1. **指望模型自觉调 save_memory 工具。** 模型会忘。**→ 后台任务自动提取**，工具方案直接放弃。
2. **提取硬凑记忆。** 没有值得记的内容也硬写，清单很快被垃圾淹没。**→ prompt 明确「空 operations 是大多数情况」**，且只记关于用户本人的持久事实，不记任务内容与闲聊。
3. **摘要带着失效的 [1][2] 引用编号。** 编号对应的 citations 不在后续上下文里，留着误导模型。**→ 摘要 prompt 明确要求剥掉**。
4. **20000 字符的报告首条消息原样喂提取模型。** 烧钱且稀释信号。**→ 单条截 2000**。
5. **记忆过时与当下冲突。** 旧记忆可能压过用户刚说的新情况。**→ `MEMORY_RULES` 规定「当下说的为准」**，且不主动复述清单。
6. **记忆无上限膨胀淹没 system prompt。** **→ 双上限**：总量 `50` 条硬顶（满了丢新记日志），注入只取最近更新 `30` 条。

### 工程健壮性（3）

1. **增强功能拖垮主链路。** **→ 失败静默**：摘要/记忆任一步失败只记日志、下一步照常；模型配置失效直接跳过；坏 JSON 宽松解析失败就跳过本轮。
2. **客户端中途断开漏跑。** 断开时后台任务不触发。**→ 全量重算兜底**：下一次成功回答把错过的补回来，无累积欠账。
3. **gunicorn 多 worker。** **→ 所有状态在 DB**，零进程内状态——这本来就是全系统的硬约束。

### 产品信任（3）

1. **AI 偷偷记住了什么，用户不知道。** **→ 设置页「长期记忆」Tab**：全量可见、可改、可删、可一键清空。
2. **所有智能体无差别积累记忆。** **→ `use_memory` 门控**：没开的智能体既不消费也不积累；内置人设里只有通用助手与求职顾问默认打开。
3. **删会话误删记忆。** **→ 语义分离**：摘要属于会话（连带删除），记忆属于用户（保留）。

## 明确的取舍（不是坑，是选择）

- **全量重算每次多烧一点 token**，换正确性和无状态——值得。
- **记忆不做结构化分类**——分类体系的维护成本远超它对注入效果的贡献，一条记忆就是一句话。
- **会话 RAG（历史会话语义检索）暂缓**——信噪比低，且引入 embedding 指纹漂移问题；结构化记忆够用之前不碰。
